# /implement-issue コマンド

ユーザーが指定した番号の GitHub Issue の内容を読み取り、その機能を実際にコードベースに実装する。

対象リポジトリは `graph-viz-with-llm`（GitHub: `MatsunoHitoshi/graph-vis-with-llm`、表示名 Ars Traverse）。マルチルートワークスペースでも、`gh` と実装作業はこのリポジトリのルートで行う。

## 手順

1. ユーザー入力から Issue 番号 N を取り出す。`13`、`#13`、Issue URL のいずれでもよい。番号が無い場合はユーザーに確認し、処理を停止する。
2. リポジトリルートで `gh issue view N --comments` を実行し、Issue の内容を取得する。必要なら `gh issue view N --json number,title,state,body,url,labels,comments` も使う。`-R` は付けない（カレントリポジトリを使う）。
3. 該当する Issue が見つからない場合、ユーザーに「指定された番号の Issue が見つかりません」と伝え、処理を停止する。
4. 既にクローズ済みの場合、ユーザーに「既にクローズ済みです。再実装しますか？」と確認する。承認がなければ停止する。
5. Issue の内容を理解し、`README.md` を読み込んでプロジェクト全体の構成を把握する。関連しそうな仕様は `docs/` 配下からも読む。
6. 必要に応じてコードベースを調査し、関連するファイルを特定する。ルーティング、執筆グラフ、共有状態に触れる場合は影響範囲も洗う。
7. プランモードに切り替え、実装計画をユーザーに提示し、確認を得る。実装は承認後に行う。
8. 実装を行う。既存のコードスタイル・パターンに従う。変更範囲が大きい場合は段階的に実装する。
9. 検証する。
   - `npm run lint`
   - ロジック変更なら `npm run test:unit`
   - UI・レイアウト・ルーティング・クライアント状態を変えた場合は、ブラウザで変更した流れを操作して確認する
10. 実装結果と残作業を日本語でまとめる。Issue はクローズしない。コミットはユーザーが明示したときだけ行う。

## 制約

- 実装前に必ずプランモードで計画を提示し、ユーザーの承認を得ること
- 既存のコードスタイル・パターンに従うこと
- 変更範囲が大きい場合は段階的に実装すること
- 実装を完了しても Issue をクローズしないこと（実装後にユーザーの希望する要件が増える可能性があるため）
- 秘密情報（`.env`、トークン、認証情報）を差分に含めないこと
- 現状の未着手タスクを勝手に Issue 化しないこと

## 例

ユーザー入力: `/implement-issue 13`

→ `gh issue view 13 --comments` で Issue 内容を取得し、プランモードで実装計画を提示、承認後に実装する。Issue はクローズしない。
